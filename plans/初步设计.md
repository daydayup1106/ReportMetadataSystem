**项目定位**

项目名我建议保留内部名 `Report Migration`，但对外展示标题不要只叫“迁移工具”，而是：

- 中文：`企业级报表知识智能平台`
- 英文：`Enterprise Report Intelligence Platform`

一句话介绍：

- `A production-grade Java platform that ingests report metadata, builds a governed knowledge base, and provides RAG/agent-powered report search, comparison, and explanation.`

这样比“Excel 转 JSON”值钱得多。

**推荐架构**

主张：`Spring Boot + LangChain4j + 企业级 Spring 生态`

核心栈：
- `Java 21`
- `Spring Boot 3.5.x`
- `Spring MVC`
- `LangChain4j`
- `PostgreSQL`
- `Redis`
- `Qdrant`
- `MinIO / S3`
- `React` 继续复用现有前端
- `SSE` 做流式回答
- `Spring Security`
- `Actuator + Micrometer + OpenTelemetry`
- `Testcontainers`
- `Docker Compose`

为什么这样配：
- `LangChain4j` 负责 `RAG / memory / tools / agent workflow`
- `Spring Boot` 负责 `安全、配置、观测、测试、交付`
- `PostgreSQL + Redis` 很像大多数 Java 团队真实生产栈
- `Qdrant` 能把你的 AI 属性做强，面试时更容易讲出深度

**模块划分**

建议做成`模块化单体`，不要首发拆微服务。

模块建议：
- `api`
  - REST + SSE 接口
  - 对前端保持稳定 API 形状
- `auth`
  - JWT / RBAC / 审计
- `report-core`
  - report、roles、config、ui settings 的核心领域模型
- `ingestion`
  - Excel 上传、解析、校验、导出
- `knowledge-index`
  - chunking、embedding、向量入库、重建索引
- `rag`
  - hybrid retrieval、metadata filter、rerank、citation
- `agent`
  - tool calling、workflow、guardrails
- `conversation`
  - chat history、memory、session summary
- `ops`
  - metrics、trace、audit log、cost tracking

**数据设计**

建议职责分清：
- `PostgreSQL`
  - 业务主数据
  - report、role、config、ui settings
  - chat_session、chat_message
  - audit_log、job_record
- `Redis`
  - 会话缓存
  - memory 摘要
  - 幂等键
  - 限流
  - 短期任务态
- `Qdrant`
  - 向量索引
  - chunk + metadata
- `MinIO/S3`
  - 原始 Excel
  - 导出 zip/json
  - 评测样本和附件

**RAG 要怎么做才像样**

不要做“用户问一句，直接向量搜一下”。

要做：
- `Hybrid Retrieval`
  - PostgreSQL 关键词/结构化过滤
  - Qdrant 向量检索
- `Metadata Filter`
  - 按 `reportId / reportType / environment / section`
- `Chunking Strategy`
  - 分块类型：
  - `report_summary`
  - `columns`
  - `parameters`
  - `roles`
  - `config`
  - `ui_settings`
- `Re-rank`
  - 初检索 topK 后再排序
- `Citation`
  - 每条回答都返回引用片段
- `No-answer Policy`
  - 没证据就说不知道
- `Evaluation`
  - hit@k
  - groundedness
  - latency
  - token cost
  - fallback rate

这是你和普通“接个大模型 API”的人拉开差距的地方。

**Agent 怎么设计**

不要做花哨多智能体，先做一个可解释的业务 Agent。

Agent 名字建议：
- `Report Intelligence Agent`

工具建议：
- `search_reports`
- `get_report_detail`
- `compare_reports`
- `find_columns`
- `explain_field_mapping`
- `show_role_by_environment`
- `export_report_package`

Agent 工作方式：
- 先判定用户意图
- 再选择工具
- 检索证据
- 生成答案
- 返回引用和置信信息

这样面试官会觉得你做的是“生产可控 agent”。

**Memory 怎么设计**

分三层：
- `history`
  - 全量消息，存 PostgreSQL
- `short-term memory`
  - 最近窗口，给模型上下文
- `summary memory`
  - 历史摘要、用户偏好、长期上下文

面试时你要能讲：
- history 不等于 memory
- 为什么不能把完整聊天历史无限塞给模型
- 怎么做摘要压缩和 token 控制

**V1 到 V3 路线**

`V1`
- 复用现有前端大部分页面
- 完成 upload / reports / roles / stats
- Query 页接入 SSE 聊天
- 支持 citation 和 session memory
- 完成 JWT、RBAC、审计、限流

`V2`
- hybrid RAG
- rerank
- compare reports
- explain field lineage
- evaluation dashboard
- token/cost/latency observability

`V3`
- MCP server
- MCP client
- agent tool marketplace
- 多租户
- 模型路由和 fallback 策略
