# 项目设计方案与实施计划

## 1. 项目定位

项目名称：`Report Migration`

对外定位：`报表元数据治理与智能检索平台`

一句话定义：

**面向报表元数据的采集、治理、检索、解释、对比、导出平台。**

系统处理对象：

- Report Metadata
- Columns
- Parameters
- Roles
- Configurations
- UI Settings
- Validation Findings
- Version Snapshots
- Audit Logs

系统明确不处理：

- 报表执行
- 邮件推送
- 调度编排
- 模板设计器
- 自动审批
- AI 自动生成正式业务事实并直接入库

## 2. V1 目标

V1 必须完成：

- Excel/JSON 元数据导入
- 元数据标准化存储
- 规则校验与问题清单输出
- 人工确认、修复、复核
- 草稿、发布、快照三层数据模型
- 报表、参数、配置、角色结构化查询
- 报表对比、版本对比、环境差异对比
- Chat/RAG 查询并返回 citation
- 完整元数据包导出
- 审计日志、AI 调用日志、基础监控
- 每个模块的单元测试和集成测试
- RAG 检索质量评测和响应时间基线

V1 不做：

- 报表引擎
- 邮件推送
- 工作流审批
- 自定义规则平台
- 多智能体自治系统
- 自动生成并保存正式 description

## 3. 设计原则

- 规则优先，AI 只做检查、解释、建议
- 结构化查询优先，RAG 只做增强
- 主业务数据与向量检索分离
- 草稿、发布、历史快照分层管理
- 所有 AI 输出默认不可直接写回正式数据
- 所有关键动作必须可审计、可回放、可追责
- Agent 受工具白名单约束，不允许自由执行未知动作
- 检索必须经过权限过滤和证据门控
- 扩展优先：新规则、新工具、新 chunk 类型可通过注册而非修改添加
- 每个模块必须有可独立运行的测试，不依赖其他模块启动

## 4. 总体架构

```text
React Frontend (reuse existing)
    |
Nginx / API Gateway
    |
Spring Boot Application (single module, package-based separation)
    |
|-- API Layer (controllers, unified response, error handling)
|-- Auth Layer (JWT, RBAC, query-time authorization)
|-- Core Layer (domain models, lifecycle state machine)
|-- Ingestion Layer (Excel/JSON parse, import job management)
|-- Governance Layer (rule engine, validation, fix, publish)
|-- Compare Layer (report diff, version diff, env diff)
|-- Knowledge Layer (chunking, embedding client, Milvus write)
|-- RAG Layer (retrieval, rerank, citation gate)
|-- Assistant Layer (intent classification, tool routing)
|-- Conversation Layer (session, memory, summary)
|-- Ops Layer (audit, AI logs, metrics, feature flags)
    |
|-- MongoDB        (business data / drafts / published / snapshots / logs)
|-- Redis          (sessions / rate limit / idempotency / short-term memory / task state)
|-- Milvus         (vector index / hybrid retrieval)
|-- MinIO/S3       (raw files / export packages)
|-- Embedding Svc  (bge-m3, sidecar, HTTP)
|-- Rerank Svc     (bge-reranker-v2-m3, co-located with embedding svc)
```

## 5. 技术选型

### 5.1 后端

- `Java 21 LTS`
- `Spring Boot 3.5.x`
- `Spring MVC` + virtual threads (`spring.threads.virtual.enabled=true`)
- `Spring Data MongoDB`
- `Spring Security`
- `LangChain4j`
- `Apache POI`
- `Jackson`
- `Gradle Kotlin DSL` (build tool)

不使用 MapStruct — MongoDB 文档模型下 DTO 转换用构造器和静态工厂方法即可，不值得引入代码生成依赖。

### 5.2 基础设施

Local Dev：

- `MongoDB 7.x`
- `Redis 7.x`
- `Milvus 2.5.x` (standalone mode)
- `MinIO`
- `Docker Compose`

Production（参见 Section 19.2 生产拓扑）：

- `MongoDB Replica Set` (3-node) 或 `MongoDB Atlas`
- `Redis Sentinel` (3-node) 或 `AWS ElastiCache`
- `Milvus Cluster` (分布式) 或 `Zilliz Cloud`
- `S3` 或 `MinIO HA`
- `Kubernetes` 或 `Docker Swarm`

### 5.3 模型与检索

Embedding：

- `bge-m3` via sidecar HTTP service
- 独立部署，不嵌入 Java 主进程
- 原因：ML 推理和业务逻辑有不同的扩展特征和部署周期；GPU 加速在独立进程中更自然；模型可替换不需重部署 Java

Reranker：

- `bge-reranker-v2-m3` co-located with embedding service
- 同一个 Python FastAPI 服务暴露 `/embed` 和 `/rerank` 端点

V1 先做 dense retrieval，V1.1/V2 扩展 sparse/hybrid。

### 5.4 可观测性

- `OpenTelemetry`
- `Prometheus + Grafana` 可后续接入

- `Testcontainers` — MongoDB / Redis / Milvus 集成测试
- `MockMvc` — API 契约测试

### 6.3 扩展点设计

以下接口设计为面向扩展开放：

V1 只设计 3 个核心扩展接口。不提前为 CSV/XML parser、ExportFormatter、audit_log chunk 等 V2+ 场景开口子。先把窄场景做深做稳。

| 扩展点 | 接口 | 注册方式 | V1 实现 | 说明 |
|---|---|---|---|---|
| 验证规则 | `ValidationRule` | `RuleRegistry.register()` | STR/FMT/UNI/CNS/GOV 共 30+ 规则 | 新增规则只需实现接口并注册 |
| Chunk 策略 | `ChunkStrategy` | Spring `@Component` 自动发现 | report_summary, columns, parameters, roles, config | 新增 chunk 类型无需改现有代码 |
| 助手工具 | `AssistantTool` | `ToolRegistry.register()` | 12 个 read-only 工具 | 新增工具只需实现接口并注册 |

V2 扩展预留（V1 不实现，仅记录方向）：

- `ReportParser` 接口 — V1 直接用 `ExcelParser` 和 `JsonParser` 具体类
- `ExportFormatter` 接口 — V1 直接输出 JSON/ZIP
- 生命周期状态扩展 — V1 用 4 状态 enum，V2 可扩展

接口设计原则：

```java
// 规则扩展示例
public interface ValidationRule {
    String ruleCode();                    // e.g., "STR-001"
    String category();                    // e.g., "structure"
    Severity defaultSeverity();           // ERROR, WARNING, INFO, REVIEW
    boolean isSync();                     // sync = blocking, async = advisory
    Optional<Finding> evaluate(Report report, ValidationContext ctx);
}

// 工具扩展示例
public interface AssistantTool {
    String name();                        // e.g., "searchReports"
    String description();                 // for LLM tool selection
    boolean isReadOnly();                 // write tools blocked in chat
    ToolResult execute(Map<String, Object> params, AuthContext auth);
}

// Chunk 策略扩展示例
public interface ChunkStrategy {
    String chunkType();                   // e.g., "columns"
    List<Chunk> chunk(Report report);     // generate chunks from report
}
```

## 7.5 写路径语义（Draft / Published 写入规则）

这是系统中最关键的语义定义。所有写操作必须遵守以下规则：

### 7.5.1 写入路径分类

| 写操作 | 路径 | 写入目标 | 触发校验 | 需要版本匹配 |
|---|---|---|---|---|
| Excel/JSON 导入 | `POST /api/upload` | → `report_drafts` (new draft) | 同步规则 | 否 |
| 确认发布 | `POST /api/upload/confirm` | draft → `reports` (publish) + `snapshots` | 检查无 error | 否 |
| 单字段修复 | `POST /api/reports/fix-field` | → `report_drafts` (edit draft) | 重跑同步规则 | 是 (version) |
| 去重列 | `POST /api/reports/remove-duplicate-columns` | → `report_drafts` (edit draft) | 重跑同步规则 | 是 (version) |
| 前端编辑已发布报表 | `PUT /api/reports/{reportId}` | → 创建新 draft → 自动校验 → 若无 error 则自动发布 + 快照 | 同步规则 | 是 (ETag) |
| 更新角色 | `PUT /api/roles/{reportId}/{env}` | → 创建新 draft → 自动校验 → 自动发布 + 快照 | 同步规则 | 是 (ETag) |
| 软删除报表 | `DELETE /api/reports/{reportId}` | → `reports.lifecycleStatus = archived` + 删除 drafts + 删除 Milvus chunks | 无 | 否 |
| 物理清除（管理员） | `DELETE /api/reports/{reportId}?purge=true` | → 物理删除 published + drafts + snapshots + findings + Milvus chunks | 无 | 需 ADMIN 角色 |
| 归档 | (new) `POST /api/reports/{reportId}/archive` | → `reports.lifecycleStatus = archived` | 无 | 是 (ETag) |

### 7.5.2 旧前端兼容写入策略

旧前端 `PUT /api/reports/{reportId}` 的期望是：编辑 → 保存 → 立即生效。

新系统的处理方式（对前端透明）：

```text
PUT /api/reports/{reportId}
  → 检查 If-Match header (ETag = publishedVersion)
  → 从 published 创建临时 draft
  → 应用前端提交的修改到 draft
  → 运行同步规则
  → 若有 error → 返回 400 + findings（前端已有 findings 展示逻辑）
  → 若无 error → 自动发布为新版本 + 写入 snapshot
  → 删除临时 draft
  → 返回更新后的 report（与旧格式一致）
```

前端不需要知道 draft 的存在。这是一个 "fast-path publish"。

### 7.5.3 并发控制

采用乐观锁（Optimistic Concurrency Control）：

draft 文档：

```json
{
  "reportId": "200012",
  "version": 3,            // ← 每次更新 +1
  "draftVersion": 1,
  ...
}
```

published 文档：

```json
{
  "reportId": "200012",
  "publishedVersion": 5,   // ← 每次发布 +1，同时作为 ETag
  ...
}
```

写入时检查：

```java
// draft 编辑 — 使用 MongoDB findOneAndUpdate with version match
Update update = new Update()
    .set("payload.columns", newColumns)
    .inc("version", 1);
Query query = Query.query(
    Criteria.where("reportId").is(reportId)
        .and("version").is(expectedVersion)  // ← OCC check
);
ReportDraft result = mongoTemplate.findAndModify(query, update, ReportDraft.class);
if (result == null) {
    throw new ConcurrentModificationException("Report was modified by another user");
}
```

旧接口的 ETag 实现：

```text
GET /api/reports/200012
Response Headers:
  ETag: "v5"

PUT /api/reports/200012
Request Headers:
  If-Match: "v5"
→ 如果当前 publishedVersion != 5 → 返回 409 Conflict
→ 前端提示 "This report has been modified by another user. Please refresh."
```

新增错误码：

| Code | HTTP Status | 说明 |
|---|---|---|
| `CONCURRENT_MODIFICATION` | 409 | 乐观锁冲突，版本不匹配 |
| `DRAFT_EXISTS` | 409 | 该报表已有未完成的 draft |

### 7.5.4 Draft 互斥规则

- 每个 reportId 同一时间最多存在 1 个 draft
- 创建 draft 时，如果已存在 draft 且 `currentEditor != 当前用户`，返回 `DRAFT_EXISTS`
- 如果 `currentEditor == 当前用户`，复用已有 draft
- draft 超过 24 小时未更新，自动标记为过期（可被其他用户覆盖）

### 7.5.5 发布语义

```text
发布条件：
  ① draft.lifecycleStatus == validated
  ② draft.validationSummary.errorCount == 0
  ③ 所有 severity=error 的 findings 状态为 fixed 或不存在

发布动作：
  ① reports collection: upsert (reportId), publishedVersion++
  ② report_version_snapshots: insert (不可变)
  ③ report_drafts: delete
  ④ reindex_jobs: create (async)
  ⑤ audit_logs: record publish action
  ⑥ change_logs: record all changes since last published version
```

### 7.5.6 删除语义

默认删除 = 软删除（归档）：

```text
DELETE /api/reports/{reportId}
  → reports.lifecycleStatus = "archived"
  → 删除该 reportId 所有 drafts
  → 删除 Milvus 中该 reportId 的 chunks（从检索中移除）
  → 保留 snapshots（不可变历史不删除）
  → 保留 audit_logs、change_logs（审计链不断裂）
  → 保留 validation_findings、validation_results（治理记录保留）
  → 记录 audit_log: action = "archive"
  → 返回 { "success": true, "message": "..." }
```

物理清除 = 管理员专用，彻底删除所有数据：

```text
DELETE /api/reports/{reportId}?purge=true
  → 需要 ADMIN 角色（非 ADMIN 返回 403）
  → 物理删除 reports collection 文档
  → 物理删除 report_drafts
  → 物理删除 report_version_snapshots
  → 物理删除 validation_results + validation_findings
  → 物理删除 Milvus chunks
  → 保留 audit_logs（purge 操作本身也要审计）
  → 保留 change_logs（操作历史保留）
  → 记录 audit_log: action = "purge", payload 包含被删除数据摘要
  → 返回 { "success": true, "message": "..." }
```

设计原因：

- 正常业务只走归档，数据可恢复
- snapshots 是不可变历史，软删除不触碰它们
- 审计链永远不断裂
- 物理清除仅用于数据治理或合规要求，有独立权限控制

## 7.7 SSE 协议定义

### 7.7.1 Chat 接口关系

两个接口的职责：

| 接口 | 用途 |
|---|---|
| `POST /api/query/chat` | 非流式问答。发送问题，等待完整回答。用于简单场景或无 SSE 支持的客户端。 |
| `POST /api/query/chat/stream` | 流式问答。发送问题，返回 SSE 流。用于 Chat 页面。 |

流式接口用 POST 而非 GET，原因：

- 用户问题放在 request body 而非 URL — 避免 URL 长度限制和 access log 泄露用户输入
- POST body 不受代理截断和编码问题影响
- 支持后续扩展（附加 filters、context 等结构化参数）

流式接口请求体：

```json
{
  "sessionId": "sess-001",
  "message": "Which reports have currency columns?",
  "filters": {}
}
```

响应：`Content-Type: text/event-stream`

前端使用 `fetch()` + `ReadableStream` 消费 SSE（非 `EventSource`，因为 `EventSource` 只支持 GET）。

前端默认使用 stream 接口。非流式接口作为降级和测试用途。

### 7.7.2 SSE Event 协议

```text
event: message_start
data: {"messageId":"msg-001","sessionId":"sess-001"}

event: token
data: {"content":"The"}

event: token
data: {"content":" report"}

event: token
data: {"content":" 200012"}

event: tool_call
data: {"toolName":"getReportDetail","input":{"reportId":"200012"},"status":"started"}

event: tool_result
data: {"toolName":"getReportDetail","latencyMs":120,"status":"completed"}

event: citation
data: {"sourceType":"report","sourceId":"200012","fieldPath":"columns[2]","snippet":"amount - Transaction amount","relevanceScore":0.92}

event: message_end
data: {"messageId":"msg-001","tokenUsage":{"inputTokens":450,"outputTokens":120},"latencyMs":3200}

event: error
data: {"code":"AI_SERVICE_UNAVAILABLE","message":"Claude API is temporarily unavailable"}
```

### 7.7.3 Event 类型定义

| Event Type | 时机 | Data 结构 |
|---|---|---|
| `message_start` | 回答开始 | `{ messageId, sessionId }` |
| `token` | 每个生成 token | `{ content }` |
| `tool_call` | 工具调用开始 | `{ toolName, input, status }` |
| `tool_result` | 工具调用完成 | `{ toolName, latencyMs, status }` |
| `citation` | 引用证据 | `{ sourceType, sourceId, fieldPath, snippet, relevanceScore }` |
| `message_end` | 回答结束 | `{ messageId, tokenUsage, latencyMs }` |
| `error` | 错误 | `{ code, message }` |
| `ping` | 心跳（每 15s） | `{}` |

### 7.7.4 断线与恢复

- 客户端使用 `fetch()` + `ReadableStream` 消费 SSE（POST 请求不支持 EventSource 自动重连）
- 服务端通过 `ping` 事件保持连接活跃（每 15s）
- 如果 SSE 连接中断：
  - 已接收的 tokens 保留在前端状态中
  - 不自动重连、不重放（POST 流不具备幂等重连语义）
  - 如需完整回答，调用 `GET /api/query/sessions/{sessionId}/messages` 获取最终持久化版本
  - 前端显示 "Connection lost. Click to retry." 由用户决定是否重新提问
- 客户端取消：调用 `AbortController.abort()` → 服务端检测到连接关闭 → 停止 LLM 生成 → 已生成部分仍保存到 chat_messages
- SSE 超时：60 秒无 token 输出 → 服务端发送 error event → 关闭连接

## 9. 生命周期设计

### 9.1 Report Lifecycle

V1 状态：

```
draft → validated → published → archived
```

状态说明：

| 状态 | 说明 | 允许操作 |
|---|---|---|
| `draft` | 工作副本，可编辑 | 编辑、修复、删除、运行校验 |
| `validated` | 规则校验通过，等待人工确认 | 确认发布、退回编辑、删除 |
| `published` | 正式版本，查询和导出可见 | 创建新 draft、归档、导出 |
| `archived` | 保留但不作为当前有效版本 | 查看、恢复为 draft |

V2 扩展预留（不改现有代码即可添加）：

```
draft → validated → pending_review → approved → published → archived
```

状态机实现要求：

```java
// 状态机设计为数据驱动，扩展新状态只需添加转换规则
public class LifecycleStateMachine {
    private final Map<StatusTransition, Predicate<Report>> transitions;
    
    public boolean canTransition(ReportStatus from, ReportStatus to, Report report) { ... }
    public void transition(Report report, ReportStatus to, String actor) { ... }
}
```

### 9.2 Import Job Lifecycle

V1 状态：

```
uploaded → processing → awaiting_confirmation → completed
                                              → failed
```

| 状态 | 说明 |
|---|---|
| `uploaded` | 文件已上传，等待处理 |
| `processing` | 解析 + 校验中（同步） |
| `awaiting_confirmation` | 存在 warning/review，等待用户确认 |
| `completed` | 处理完成，数据已入库 |
| `failed` | 处理失败 |

### 9.3 Finding Lifecycle

```
open → accepted / fixed / ignored
```

| 状态 | 说明 |
|---|---|
| `open` | 新发现，等待处理 |
| `accepted` | 人工确认接受（warning/review 类） |
| `fixed` | 已修复 |
| `ignored` | 人工判定忽略 |

## 11. 检索设计

### 11.1 Retrieval Pipeline

V1：

1. 鉴权 — 用户身份和权限
2. intent classification — 判断查询类型
3. 能走结构化查询则直接查 MongoDB（优先）
4. 否则调用 embedding service 生成查询向量
5. Milvus dense search + metadata filter
6. 调用 rerank service 对 top-K 重排序
7. citation gate — 验证证据充分性
8. 生成回答

### 11.2 Citation Gate

回答前必须满足：

- 至少命中 1 条有效证据
- 证据与问题意图相关（reranker score > threshold）
- 证据对象用户有权限访问
- 证据来自 published 版本（不引用 draft）

不满足时：

- 返回 "未找到足够证据回答此问题"
- 记录 refusal 到 ai_interaction_log
- 不允许模型自由编造

### 11.3 权限过滤

所有检索前必须做：

- MongoDB 查询附加 `lifecycleStatus: "published"` 过滤
- Milvus 查询附加 `access_tags` 过滤
- citation 返回也过滤权限

## 12. 规则引擎设计

### 12.1 规则分层

同步阻断规则（导入时立即执行）：

- 结构完整性 (STR-*)
- 格式规范 (FMT-*)
- 唯一性 (UNI-*)
- 关键一致性 (CNS-001, CNS-002)

异步复核规则（后台异步，不阻塞导入）：

- 语义与治理规则 (GOV-*)
- 一致性建议 (CNS-003 ~ CNS-007)
- 可运维性 (OPS-*)

### 12.2 规则注册

```java
@Component
public class StructureRules {

    @PostConstruct
    public void register(RuleRegistry registry) {
        registry.register(syncRule("STR-001", "structure", ERROR,
            report -> isEmpty(report.getReportId()),
            "reportId is required"));
        
        registry.register(syncRule("STR-002", "structure", ERROR,
            report -> isEmpty(report.getReportName()),
            "reportName is required"));
        
        // ... more rules
    }
}
```

新增规则：创建新的 `@Component` 类，实现 `ValidationRule` 接口并注册。无需修改 `RuleEngine` 或任何已有规则类。

### 12.3 规则版本化

每次执行记录：

- `rulesetVersion`：规则集版本号（手动维护）
- 执行时间
- 执行对象版本
- 执行结果

### 12.4 入库策略

- 有 `error`：禁止确认发布
- 仅有 `warning/info/review`：允许人工确认
- AI review 永远不能直接标记为正式事实

## 13. Chat / Assistant 设计

V1 采用：

## 14. Memory 设计

### 14.1 三层架构

#### History（完整消息记录）

- 存储：MongoDB `chat_messages` 集合
- 用途：审计、回放、评测
- 保留策略：按 session 保留全部，session 级 TTL 可配置

#### Short-term Memory（当前对话窗口）

- 存储：Redis
- 内容：最近 N 轮消息（默认 10 轮 = 20 条 user+assistant）
- 用途：传给 LLM 作为对话上下文
- 附加上下文：当前 reportId、filters、last intent
- TTL：30 分钟

#### Summary Memory（会话摘要）

- 存储：MongoDB `chat_sessions.summaryText`
- 生成时机：当 short-term window 滑动丢弃消息时
- 用途：压缩历史上下文，控制 token 成本
- 生成方式：LLM 调用生成摘要

### 14.2 Memory Flow

```text
User sends message
    → Load short-term memory from Redis (recent N messages)
    → Load summary from MongoDB (if exists)
    → Compose context: [system prompt] + [summary] + [recent messages] + [new message]
    → Send to LLM
    → Save assistant response to MongoDB (history)
    → Update Redis short-term memory (sliding window)
    → If window overflow, trigger summary regeneration
```

V1 不做：

- 跨会话长期个性化偏好学习
- 自动任务规划

## 17. 关键流程

### 17.1 导入与确认发布

```text
上传文件
→ 存储原文件到 MinIO
→ 创建 import_job (status: uploaded)
→ 解析 Excel/JSON (status: processing)
→ 写入 report_draft (status: draft)
→ 执行同步规则引擎
→ 生成 validation_result + findings
→ 更新 draft (status: validated) 或保持 draft（如有 error）
→ 返回 findings 给前端
→ 用户修复 / 确认
→ 发布为正式版本 (status: published)
→ 写入 snapshot
→ 触发异步 reindex job
→ 记录 audit_log
```

### 17.2 修复流程

```text
编辑 draft 字段
→ 记录 change_log
→ 运行同步规则
→ 更新 findings 状态
→ 可选触发异步 AI review
→ 返回更新后的 findings
```

### 17.3 索引流程

```text
读取 published report
→ 按 chunk strategy 生成 chunks
→ 调用 embedding sidecar 生成 embeddings
→ 写入 Milvus（upsert by report_id + chunk_type）
→ 更新 reports.indexStatus = "indexed"
→ 记录 reindex_job
→ 失败时标记 indexStatus = "index_failed" 并支持重试
```

### 17.4 Chat/RAG 流程

```text
用户提问
→ 鉴权
→ 加载 short-term memory + summary
→ intent classification
→ 如果是结构化查询 → 直接查 MongoDB
→ 否则 → embedding service → Milvus search → rerank service
→ citation gate (验证证据充分性)
→ tool-routed assistant 整理答案
→ SSE 流式返回
→ 保存 chat_message + ai_interaction_log
→ 更新 Redis short-term memory
```

### 17.5 对比流程

```text
读取两个报表或两个版本的 published payload
→ 结构化 diff (columns / parameters / roles / config)
→ 输出差异结果
→ 可选 AI 生成差异摘要
→ AI 摘要作为附加信息，不改变原始 diff 结果
```

## 19.2 生产拓扑（Production Topology）

本地 Docker Compose 拓扑仅用于开发和功能验证。生产环境有不同的 HA、备份、扩容、滚动升级要求。

### 生产 vs 本地对比

| 组件 | Local Dev | Production | 差异说明 |
|---|---|---|---|
| **Spring Boot** | 单实例 | 2+ 实例 (behind LB) | 水平扩展，无状态设计 |
| **MongoDB** | 单节点 | 3-node Replica Set 或 Atlas | HA + 自动故障转移 + 备份 |
| **Redis** | 单节点 | Sentinel (3-node) 或 ElastiCache | HA + 自动故障转移 |
| **Milvus** | Standalone | Cluster (分布式) 或 Zilliz Cloud | HA + 扩容 + 滚动升级 |
| **MinIO** | 单节点 | S3 或 MinIO HA (4+ node) | 持久性保证 |
| **Embedding Svc** | CPU, 单实例 | GPU, 2+ 实例 | 吞吐量 + 故障隔离 |
| **Nginx** | 不使用 | Nginx / ALB | SSL 终止 + 反向代理 + 限流 |

### 生产关键运维点

| 关注点 | 策略 |
|---|---|

| **RPO** | MongoDB: < 1 min (oplog); Milvus: < 24h (可重建); Redis: < 5 min |

## 23. 风险与控制

风险：

- 范围失控，想做成完整报表平台
- AI 职责过宽，开始生成正式业务事实
- Query 设计过于开放，导致不可控
- 检索质量不足但提前上 Chat
- 草稿与发布态混淆
- 向量检索未做权限过滤
- 测试不充分导致上线后回退
- Embedding sidecar 不稳定影响核心功能

控制措施：

- 严格遵守业务边界
- AI 只做检查、解释、建议
- 结构化查询优先
- Chat 只走工具白名单
- 发布前必须经过 citation gate
- 先评测检索质量，再开放 Query
- 每个 phase 必须通过测试才进入下一 phase
- Embedding sidecar 不可用时降级为纯结构化查询

## 25. V1 验收标准

功能验收：

- 可导入样例 Excel/JSON 并写入 draft
- 存在 error 时不能确认发布
- 可查看 findings 并进行人工修复
- 可将通过复核的数据发布为正式版本
- 可生成不可变版本快照
- 可查询报表/参数/配置/角色详情
- 可比较报表和版本差异
- Chat/RAG 仅回答约定范围内问题
- 每次回答返回 citation 或明确拒答
- 检索结果经过权限过滤
- 可触发单报表与全量 reindex
- 所有关键操作有审计日志
- AI 调用可追踪 token、latency、tool trace
- 基础监控、健康检查可用

质量验收：

- 单元测试覆盖率 > 80%（核心业务 > 90%）
- 所有 API contract tests 通过
- 响应时间基线全部达标
- RAG 质量指标：
  - Intent Accuracy >= 85%
  - Retrieval Hit@5 >= 75%
  - Citation Precision >= 80%
  - Groundedness >= 90%
  - No-Answer Accuracy >= 90%
  - Hallucination Rate <= 5%
- 负载测试无内存泄漏
- Embedding sidecar 降级策略验证通过

运维验收：

- Docker Compose 一键启动
- 部署文档完整
- 运行手册完整
- 备份恢复策略已验证
